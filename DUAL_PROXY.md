# Режим «Dual Proxy» (Двойной параллельный прокси) в Throne

Этот форк добавляет полноценную нативную поддержку одновременной работы **двух независимых прокси-серверов** на разных локальных портах прямо из графического интерфейса.

---

## Как это можно было сделать в оригинале?

В официальном Throne (и Nekoray) технически **тоже можно** организовать второй локальный порт, используя встроенные низкоуровневые возможности ядра:
1. Зайти в **Основные настройки** -> блок **Пользовательский инбаунд (Custom Inbound)**.
2. Вручную написать сырой JSON-фрагмент для `sing-box`, объявив второй входящий порт (например, `mixed` на порту `2081` с тегом `secondary-in`).
3. Перейти в **Настройки маршрутизации** и вручную добавить JSON-правило маршрутизации, связывающее `inbound: ["secondary-in"]` с тегом нужного аутбаунда.
4. Либо запускать два отдельных экземпляра Throne с разными флагами `-appdata` и разными портами.

---

## Почему я решил сделать нативно из коробки?

Хотя в оригинале это возможно через правку конфигурационных JSON, на практике такой подход крайне неудобен для повседневного использования. Вот почему в этом форке всё реализовано нативно на уровне ядра и UI:

### 1. Переключение сервера в 1 клик (без правки JSON)
В оригинале при желании сменить страну или сервер для второго прокси приходится снова открывать настройки, искать тег профиля в JSON и переписывать правило роутинга.  
В этом форке: **правый клик по любому профилю в списке ➔ «Сделать вторым прокси...»** — ядро перезапускается с новой конфигурацией, включающей оба прокси. **Внимание:** при смене secondary-сервера происходит полный перезапуск ядра — все активные соединения на обоих портах будут кратковременно разорваны.

### 2. Интерактивный выбор и смена порта прямо в интерфейсе
- При назначении второго прокси появляется окно выбора порта (по умолчанию `2081`, диапазон 1024–65535, с проверкой пересечения с портом основного прокси, DNS-входа ядра, Clash API, API панели и удалённого API).
- В контекстном меню есть отдельное действие **«Изменить порт второго прокси...»** для быстрой смены порта на лету.
- Порт также вынесен в интерфейс **Основных настроек** (Inbound Settings) для централизованного управления.

### 3. Полный визуальный контроль и информативность
В оригинале при ручной настройке GUI «не знает» о существовании второго прокси. В нашем форке:
- **В таблице профилей**: сразу видно роли серверов по бейджам и цветам — `[1st:2080]` (основной) и `[2nd:2081]` (второй). Назначенный, но не запущенный secondary помечается бейджем без цвета.
- **В строке состояния внизу окна**: выводятся оба сервера, их внешние IP-адреса и страны с флагами:
  - `1st: [default] Germany (🇩🇪 Germany, Frankfurt)`
  - `2nd: Netherlands (🇳🇱 Netherlands, Amsterdam)`
  - `Mixed: 127.0.0.1:2080 | 2nd: 2081`
- Геолокация и флаг для каждого прокси определяются независимо через соответствующие порты (тем же провайдером, что выбран в настройках).
- На графике скорости у secondary своя линия «2nd», трафик учитывается в строке его профиля.

### 4. Нативная поддержка в мониторе соединений (Connections)
Второй инбаунд автоматически регистрируется в системе статистики. Во вкладке **Соединения** отображаются все активные процессы, трафик, скорость и целевые хосты как для основного порта `2080`, так и для второго порта `2081`; в колонке Outbound — имя профиля.

### 5. Без DNS-утечек между прокси
Всё, что пришло на порт secondary (включая DNS-запросы), уходит в цепочку secondary до правил `resolve` и `hijack-dns` основного прокси. Если secondary — endpoint (WireGuard, Tailscale, MASQUE) и сам резолвит адреса назначения, он делает это через отдельный сервер `dns-secondary`, который ходит через цепочку secondary; кэши DNS двух прокси разделены.

## Краткая инструкция по использованию

1. Запустите основной сервер обычным способом (клавиша **Enter** или кнопка «Запустить») — он будет слушать на порту `127.0.0.1:2080`.
2. Кликните правой кнопкой мыши по серверу, который хотите использовать параллельно, и выберите **«Сделать вторым прокси...»**:
   - Введите желаемый порт (например, `2081`).
   - Сервер будет помечен значком `[2nd:2081]`.
3. Настройте приложение (браузер, Telegram, торрент-клиент или игру) на прокси `127.0.0.1:2081` (поддерживаются протоколы SOCKS5 и HTTP).
4. Основная система и приложения используют `127.0.0.1:2080` (или системный прокси/TUN), а отдельное приложение ходит через второй сервер на `127.0.0.1:2081`.
5. Чтобы отключить второй прокси — правый клик ➔ **«Отключить второй прокси»**.

## English Summary

**Dual Proxy Mode Fork**:
While original Throne/Nekoray allows configuring secondary inbounds manually via custom JSON and route rules, it requires manual maintenance and lacks UI feedback. This fork introduces **native Dual Proxy support**:
- 1-click profile assignment from context menu (**"Set as Secondary Proxy..."**).
- Interactive port picker & runtime port change without restarting the app.
- Clear UI indicators (`[1st:2080]` and `[2nd:2081]` badges in the server table).
- Dual status display with independent IP and country flag resolution in the status bar.
- Live connections and per-process traffic tracking for both inbounds in the Connections tab, with a separate "2nd" speed-graph line.
- Secondary traffic, DNS included, never goes through the primary's DNS rules or upstream.
- Persistent primary profile memory across app restarts.

---

## Известные ограничения / Known Limitations

1. **Перезапуск ядра при смене secondary**: назначение, смена или отключение secondary-прокси перезапускает sing-box целиком — все активные соединения на обоих портах кратковременно рвутся. Горячая перезагрузка без разрыва primary пока не реализована.
2. **Пользовательские правила маршрутизации не применяются к secondary-трафику**: весь трафик с порта secondary безусловно направляется в secondary-outbound (включая DNS). LAN bypass, adblock, GeoIP/GeoDomain-правила — всё пропускается.
3. **Недопустимые типы secondary**: автовыбор, extra core, полные конфигурации (sing-box / Xray), OpenVPN и OpenConnect (и цепочки с ними). Xray-профиль также нельзя сделать secondary, если основной профиль — полная конфигурация Xray. Такой secondary не запускается, причина пишется в лог, primary стартует как обычно.
4. **Полная конфигурация sing-box как primary** запускается как есть, порт secondary при этом не открывается.
5. **Собственный DNS-объект** (`use_dns_object`): если DNS задан сырым JSON, сервер `dns-secondary` не добавляется — endpoint-профили на secondary резолвят имена по вашим правилам.
6. **Headless / удалённый API**: настройки Dual Proxy пока нельзя менять через `thronectl` и REST API (заданные в GUI настройки headless-режим применяет).

## Сборка / Building

GUI (`Throne.exe`) и ядро (`ThroneCore.exe`) должны собираться **из одного коммита**. Релизы v1.3.0 / v1.3.0-dp.1 собирались с ядром из публичного релиза, и в GUI пришлось отключить `QueryVPNStatus`, сервис `api` (статистика, панель) и `store_dns`. Эти обходы удалены, поэтому со старым ядром новая сборка работать не будет.

Workflow `.github/workflows/dualproxy-windows.yml` собирает оба компонента из одного коммита на каждый push / pull request и выкладывает артефакт `Throne-<версия>-windows64-dualproxy.zip`. Локальная сборка повторяет шаги этого workflow: `GOOS=windows GOARCH=amd64 ./script/build_go.sh` для ядра, затем CMake + Ninja (MSVC, Qt 6) для GUI.

The GUI and `ThroneCore.exe` must come from the same commit; the workflow above builds both and packs the Windows x64 zip.

## Changelog

### 2026-10-21 — Синхронизация с upstream `dev` (`72c70df4`, после 1.4.0-beta.3)

**Перенос на новую архитектуру upstream:**

- Логика запуска перенесена из `MainWindow::profile_start` в `Engine::ConnectionManager` (upstream вынес старт и остановку в движок). Secondary работает и при запуске из трея, горячей клавиши, REST API и в headless-режиме.
- Определение страны secondary использует новый `ExitLookup` upstream (выбранный в настройках провайдер с запасными); запрос идёт через порт secondary (`HttpGetOptions::inboundPort`).
- Действия контекстного меню вынесены в `mainwindow_dualproxy.cpp`, чтобы будущие слияния с upstream давали меньше конфликтов.

**Исправленные баги:**

- 🔴 **Обходы под старое ядро удалены**: заглушка `QueryVPNStatus` (ломала вход OpenVPN/OpenConnect), отключённый сервис `api` (статистика, панель), `store_rdrc` вместо `store_dns`, `value_or` и глушащий всё `try/catch` в мониторе соединений.
- 🟠 **DNS-утечка через `resolve`**: `secondary-in` был в правиле `resolve`, и при заданной стратегии резолва имена для secondary резолвились через DNS основного прокси. Правило secondary теперь стоит сразу после `sniff`, до `resolve` и `hijack-dns`. Ограничение `hijack-dns` только на `mixed-in`/`tun-in` снято (оно отключало перехват DNS для пользовательских inbound).
- 🟠 **DNS-утечка для endpoint-профилей**: WireGuard / Tailscale / MASQUE на secondary резолвили назначение через `dns-remote` по основному прокси. Добавлен сервер `dns-secondary` с `detour` через цепочку secondary и правило `inbound: secondary-in`; кэши DNS разделены (`independent_cache`).
- 🟠 **Удаление группы** с secondary-профилем оставляло `secondary_profile_id`, указывающий на удалённую строку. Очистка перенесена в `ProfilesRepo::DeleteAndForget` (общий путь для профилей и групп) и выполняется в UI-потоке (обновление подписки удаляет профили из рабочего потока).
- 🟠 **Удалённый работающий secondary** продолжал слушать порт без предупреждения — теперь появляется стандартное уведомление «нужен перезапуск».
- 🟠 **Устаревший ответ геолокации**: проверка `running->id == startedId` не ловила перезапуск того же primary (например, при смене secondary). Теперь используется счётчик запусков secondary.
- 🟡 **Группа secondary**: front/landing proxy группы secondary-профиля теперь применяются, как при обычном запуске.
- 🟡 **Проверка профиля**: одна функция `SecondaryProxyProblem()` используется и в меню, и в генераторе (раньше генератор тип не проверял).
- 🟡 **Порты**: `SecondaryPortConflict()` проверяет диапазон 1024–65535 и пересечение с mixed, DNS-in, Clash API, API панели и удалённым API. В «Основных настройках» тихая подстановка `порт+1` (могла дать 65536) заменена ошибкой валидации. Окно выбора порта переспрашивает вместо отмены.
- 🟡 **Бейджи**: `[2nd:порт]` виден и при остановленном ядре (без цвета, с подсказкой «не запущен»); цвет и `[1st]` — только когда работающий конфиг действительно обслуживает secondary. Подсказка бейджа больше не перекрывает предупреждение о безопасности в колонке «Тип».
- 🟡 **Строка состояния** показывает то, что реально запущено; порт secondary виден, даже если mixed-inbound отключён.
- 🟡 **Автовыбор профиля для запуска** (Enter без выделения, трей, горячая клавиша) больше не выбирает secondary-профиль — иначе его назначение сбрасывалось.
- 🟡 **Резервные копии / WebDAV**: при восстановлении `primary_profile_id` и `secondary_profile_id` проверяются так же, как `remember_id`.
- 🟡 `.gitignore`: `/dist` заменён на `/release/` — upstream теперь хранит в `dist/` файлы упаковки.

**Закрытые ограничения:** отдельная линия «2nd» на графике скорости и учёт трафика в строке профиля; в мониторе соединений вместо `secondary-0` показывается имя профиля.

### 2026-09-16 — Bugfix Patch

**Исправленные баги:**

- 🔴 **Critical**: Удаление профиля, назначенного secondary, больше не ломает запуск ядра. Добавлена автоматическая очистка `secondary_profile_id` при удалении и защита в генераторе конфига (`generate.cpp`, `ProfilesRepo.cpp`).
- 🔴 **Critical**: Профили типа `autoselector` и `extracore` теперь заблокированы от назначения secondary — UI показывает предупреждение (`mainwindow_setup.cpp`).
- 🟠 **DNS-утечка**: DNS-запросы от secondary-трафика больше не перехватываются и не резолвятся через primary proxy. Правило `dns-hijack` теперь ограничено только `mixed-in` и `tun-in` (`generate.cpp`).
- 🟠 **Data race**: Запись `runningCountryInfo` перенесена в UI-поток, устранено undefined behavior при конкурентном доступе (`mainwindow_profile_lifecycle.cpp`).
- 🟠 **Stale callback**: Geolocation-запрос теперь проверяет, что текущая сессия не изменилась, прежде чем обновлять UI.
- 🟡 **Бейдж `[2nd]`**: больше не отображается зелёным при остановленном ядре (`ProfilesTableModel.cpp`).
- 🟡 **Коллизия портов**: при совпадении secondary и primary порта в Basic Settings порт автоматически корректируется (`dialog_basic_settings.cpp`).
- 🟡 **Raw routing**: secondary-правило теперь инжектируется даже в raw routing-профили с `preventModifications = true` (`generate.cpp`).
- 🟡 **Пустая страна**: при ошибке `ip-api.com` строка статуса больше не показывает `" , "`.
- 📝 **Документация**: убрано ложное утверждение «без разрыва основного подключения».
